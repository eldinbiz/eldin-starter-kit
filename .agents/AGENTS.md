# Workspace Rules

## AI Assistant Directives

### 1. Spec-First Development (OpenSpec Protocol)
- **Always operate in Planning / Consultation mode by default.**
- **Do NOT modify, create, or delete code files directly** on initial requests or exploratory turns.
- For all new features, refactors, architectural modifications, and non-trivial changes, use the OpenSpec workflow:
  1. **Explore (`/openspec-explore`)**: Clarify ambiguous requirements, investigate the codebase, and evaluate options before proposing. Never make silent assumptions on ambiguous requirements.
  2. **Propose (`/openspec-propose`)**: Generate a structured change proposal in `openspec/changes/<change-name>/` containing `proposal.md`, `specs/`, `design.md`, and `tasks.md`.
  3. **Halt for Approval**: Present the proposal link (`[proposal.md](file:///...)`) to the user and prompt them to review before any implementation begins.
  4. **Apply (`/openspec-apply-change`)**: Execute implementation task-by-task strictly after explicit authorization.
  5. **Archive (`/openspec-archive-change`)**: Absorb verified changes into living specifications under `openspec/specs/`.

### 2. Mandatory Human Approval Before Execution
- **Explicit User Approval Required**: The assistant must never execute `apply` or modify code files until the user explicitly replies with "Proceed", "Go", "Apply the change", or equivalent direct confirmation.
- Never dump raw unformatted code or execute multi-file changes without an approved change proposal.

### 3. Forbidden File Modifications (vendor/ & node_modules/)
- **Strictly Prohibited:** The assistant MUST NEVER modify, patch, create, or delete any files inside `vendor/`, `node_modules/`, or `.git/`.
- All third-party package adjustments, bug workarounds, or custom behaviors must be implemented in application space (`app/`, `app-modules/`, `config/`, or Service Providers) or managed via Composer/NPM. Never attempt to patch vendor packages directly.

### 4. Bug Fixing & Diagnostic Mode Protocol
- **No Immediate Code Changes on Bug Reports:** When investigating reported bugs, UI defects, unexpected behavior, or test failures, do NOT immediately apply code fixes.
- **Read-Only Diagnosis First:**
  1. Inspect relevant log files (e.g. `doctest-reports/test-log/` or `doctest-reports/browser-test-log/`), stack traces, database states, and Blade/JS source.
  2. Explain the **Root Cause** of why the failure or defect occurs.
  3. If there are ambiguities in how to remediate, ask clarifying questions first.
  4. For non-trivial bug fixes, propose remediation via OpenSpec before editing code.
- **Wait for Confirmation:** Always wait for explicit user approval (e.g., clicking *"Proceed"* or replying *"Apply the fix"*) before modifying any files.

## Terminal Command Execution
- **Ask Before Execution:** Whenever a terminal command needs to be executed (such as running migrations, installing packages, starting servers, tests, etc.), present the exact command clearly with context explaining what it does and why it is needed.
- **User Preference Options:** Ask the user whether they prefer to:
  1. Run the command themselves in their terminal, OR
  2. Let the agent execute it on their behalf to capture output, inspect logs, and automatically debug/fix errors.
- **Execute Only Upon Explicit Permission:** The agent may only execute terminal commands via tools when the user explicitly chooses or confirms for the agent to run them.

## Git Branching & Merge Policy
- **Always Work on `development`:** Perform all edits, commits, and active development directly on the `development` branch. Only create a feature branch (branched off `development`) if explicitly requested by the user.
- **Pre-Flight Branch Guard:** Before modifying files or committing, verify the active branch is `development`. If checked out on `main`, `staging`, or detached `HEAD`, stop and switch to `development` first (following Terminal Command Execution permission rules).
- **`staging` Merges Only on Command:** Never checkout, merge into, push to, or open PRs targeting `staging` unless explicitly commanded by the user. After an authorized merge from `development` into `staging`, immediately switch back to `development`.
- **Strict `main` Protection (GitHub UI Only):** The user merges changes into `main` manually via the GitHub UI. The assistant MUST NEVER checkout `main` to work, commit to `main`, merge into `main`, push to `main`, or create/merge Pull Requests targeting `main`.
- **Detailed Specification:** Follow [git_branching.md](rules/git_branching.md) whenever planning or executing branch, commit, merge, or PR operations.

## Test Failure Diagnostics
- **Always Read the Latest Test Log File**: When investigating test failures generated by Pest, ALWAYS read the latest `*.log` file from the dedicated directory using the `list_dir` and `view_file` tools:
  - For Unit/Feature tests (`rubberstamp:features`): inspect the latest `test_*.log` file in `doctest-reports/test-log/`.
  - For Browser tests (`rubberstamp:browser`): inspect the latest `browser_test_*.log` file in `doctest-reports/browser-test-log/`, review the corporate audit report in `doctest-reports/browser_test_{timestamp}.html`, and check visual snapshots in `doctest-reports/browser-test-log/browser_test_{timestamp}/<Suite-Name>/<test_case_slug>.png`.
  Do not rely exclusively on terminal output snippets provided by the user, as they may be truncated, mixed with TTY escape sequences, or out of date.

## 3-Layer + Livewire v4 Architecture Standard

### 1. Presentation Layer (Thin Controllers & Livewire v4 Components)
- **Thin Controllers (`app/Http/Controllers/` or `Modules\<Module>\Http\Controllers\`):** Must contain only HTTP transport logic (injecting requests and actions, delegating to action `execute()`, and returning responses). No raw database updates, transactions, or heavy domain logic in controllers.
- **Livewire v4 Components (`app/Livewire/` or `Modules\<Module>\Livewire\`):** Serve as reactive UI orchestrators in the Single Page Application (SPA).
  - Must declare `declare(strict_types=1);` and be `final class`.
  - Use `#[Url]` for query string binding, `#[Computed]` for cached query properties, and `#[Validate]` or Form Objects for validation.
  - **Mutation Rule:** For any database updates, creation, or deletion, Livewire component methods MUST delegate to **Domain Actions** (`$action->execute(...)`). Never write inline transactions or direct multi-table Eloquent mutations directly in component classes.
  - **SPA Navigation:** Always use `wire:navigate` and `wire:navigate.hover` on internal links to guarantee smooth SPA transitions with zero full-page reloads.
  - **Multi-Theme UI Component Standard:** All views, Livewire components, and domain modules must consume abstract `<x-ui::*>` components (`<x-ui::card>`, `<x-ui::button>`, `<x-ui::input>`, `<x-ui::modal>`, `<x-ui::table>`) governed by the `ui-themes` skill to ensure 100% theme portability across all configured themes (`shadcn`, `tailadmin`). Never write raw theme-specific classes directly in page templates.

### 2. Validation & Authorization Layer (Form Requests)
- **Form Requests (`app/Http/Requests/` or `Modules\<Module>\Http\Requests\`):** Must be `final class`, declare `declare(strict_types=1);`, enforce permission/company authorization in `authorize(): bool`, and return validation rules in `rules(): array`.

### 3. Domain Business Layer (Domain Actions)
- **Domain Actions (`app/Actions/` or `Modules\<Module>\Actions\`):** Must be `final class`, declare `declare(strict_types=1);`, encapsulate multi-table modifications inside `DB::transaction()`, dispatch domain events/notifications, and expose a single public `execute(...)` method.
- **Domain Modules:** Apply the exact same 3-layer pattern inside `app-modules/<module>/` (`Modules\<StudlyName>\Actions\*`, `Modules\<StudlyName>\Livewire\*`, `Modules\<StudlyName>\Http\Requests\*`).
